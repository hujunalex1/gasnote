# 加油记账（gasnote）设计文档

日期：2026-10-15
状态：已获用户批准，待生成实现计划

## 1. 目标

一个记录每次加油金额、并按月/按年统计的个人记账小工具。

核心问题：**我这个月、今年到底在油上花了多少钱，哪个月花得特别多？**

成功标准：
- 记一笔账只需输入两个值（日期、金额），3 秒内完成。
- 打开页面立刻看到本月、本年合计，不需要任何点击。
- 能看到所选年份 12 个月的分布，一眼看出哪个月是高峰。
- 数据在关掉浏览器后仍然存在，且能导出一份文件自己留底。

## 2. 非目标（YAGNI）

明确不做，理由记在此处，避免实现时反复动摇：

| 不做 | 理由 |
|---|---|
| 里程、升数、单价、油耗 | 用户明确选择"只记日期+金额"。油耗是最容易被加进来的功能，但用户不要。 |
| 车辆维度 | 单用户单设备，后续真要加也不痛：老记录无 `vehicleId` 即默认归唯一一辆车。 |
| 多用户 / 账号系统 | 单用户单设备，纯前端。 |
| 后端 / 数据库 | 同上。数据存 localStorage。 |
| Chart.js 等图表库 | 12 根柱子的柱状图用 CSS `height` 百分比就够，不值得引入依赖。 |
| 部署到 Vercel/Pages | 用户未要求。属"5 分钟就能加"的可选步骤。 |
| 预算/超支提醒 | 未要求。 |
| 编辑已有记录 | 第一版只支持新增和删除。记错了就删掉重记。 |

## 3. 技术选型

**零构建原生 ES Module**。零依赖、零打包、零 `npm install`。

- 语言：原生 JavaScript（非 TypeScript），浏览器原生 `import`。
- 样式：单个手写 CSS 文件。
- 测试：Node 内置 `node --test`，不安装任何包。
- 运行：`python3 -m http.server 8000`（或任意静态服务器），浏览器开 `http://localhost:8000`。

**为什么不用 Vite + React**：本工具共 4 个源文件、2 个输入字段、3 个统计函数。构建链带来的收益为零，而 `node_modules` 的腐坏风险是非零的——一年后再 `npm install` 可能已经跑不起来。原生 ES Module 拿到了模块化的清晰度，同时保证十年后双击还能跑。

**为什么不能双击 `index.html` 直接打开**：macOS 上 Safari 在 `file://` 协议下禁用 localStorage，数据存不住。必须经 HTTP 提供。

## 4. 文件结构

```
gasnote/
├── README.md              # 怎么跑、怎么备份、怎么恢复
├── index.html             # 页面骨架
├── styles.css             # 全部样式
├── src/
│   ├── store.js           # localStorage 读写 + 导入导出校验
│   ├── stats.js           # 纯统计函数
│   └── ui.js              # DOM 渲染 + 事件绑定
├── test/
│   ├── stats.test.js
│   └── store.test.js
└── docs/superpowers/specs/2026-10-15-gasnote-design.md
```

职责边界：

- `stats.js` —— **纯函数，不碰 DOM、不碰 localStorage、不读 `Date.now()`**。输入数组，输出数字和对象。这是唯一有真实逻辑的模块，也是唯一做单元测试的模块。
- `store.js` —— 负责持久化。`load()` / `save()` 直接操作 localStorage；`parseImport()` 是纯函数（只吃字符串，吐出校验结果），因此可测。
- `ui.js` —— 唯一接触 DOM 的模块。读用户输入、调 `store` 持久化、调 `stats` 算数、画界面。不做业务判断。

## 5. 数据模型

localStorage key：`gasnote.records.v1`

```json
{
  "version": 1,
  "records": [
    { "id": "a3f8c1e2-...", "date": "2026-10-15", "amount": 320.5, "note": "" }
  ]
}
```

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识。优先 `crypto.randomUUID()`；若不可用（非 secure context，例如通过局域网 IP 访问）则回退到时间戳+随机数拼接。 |
| `date` | string | 格式严格为 `YYYY-MM-DD`。**存字符串，不做 `Date` 对象序列化**——那会引入时区偏移，导致晚间录入被记到前一天。 |
| `amount` | number | 单位：元。保存前舍入到 2 位小数。 |
| `note` | string | 可选备注，默认 `""`。 |

关键约定：

- **归属月份 = 月份 key = `date.slice(0, 7)`**（如 `"2026-10"`）。纯字符串截取，不做日期解析，天然无时区问题。
- **求和时一律转成整数"分"累加，最后再除回 100**。直接累加浮点元数会导致 `0.1 + 0.2` 类误差在几十条记录后漂成 `¥1240.5000000000002`。即 `cents = Math.round(amount * 100)`，累加后再 `/ 100` 显示。
- 记录列表默认排序：按 `date` 降序；同一天内按录入顺序倒序（最新录入在前）。`records` 数组本身即按录入顺序追加，所以"新的在前"= 过滤后 `reverse()`，**不需要额外的 `createdAt` 字段**。
- `version` 字段用于将来迁移。**读到不认识的版本时绝不静默丢弃**：把原始字符串原样备份到 `gasnote.records.v1.corrupt` 键，以空数据启动，并在页面顶部红色横幅明确告知"检测到本工具更新版本写入的数据，原始副本已保留"。宁可让用户看到空列表并被告知，也不能让数据无声消失。

## 6. 统计逻辑（`src/stats.js`）

三个纯函数，全部无副作用：

```js
monthlyTotal(records, "2026-10") -> { total, count, avg }
yearlySummary(records, 2026)     -> { total, count, months: [{ month, total, count }, ...] }
allYears(records)                -> [2026, 2025, 2024]
```

语义：

- `monthlyTotal` —— 过滤出月份 key 匹配的记录。`total` 为金额合计，`count` 为加油次数，`avg` 为平均每次金额。
- `yearlySummary` —— `months` **恒定返回 12 项**，无论该月有无记录（无记录的月份为 `{ total: 0, count: 0 }`）。这保证柱状图永远画得出 12 根柱子。
- `allYears` —— 从记录中提取所有出现过的年份，降序排列。**当前年份始终包含在内**，即使当年一条记录都没有（否则年份选择器会是空的，用户无法在无数据的新年份里记账）。

边界情况（全部写进单元测试）：

| 输入 | 期望输出 |
|---|---|
| 空数组 | `{ total: 0, count: 0, avg: 0 }`，**不是 `NaN`** |
| 该月无记录 | `{ total: 0, count: 0, avg: 0 }` |
| 该年无记录 | `{ total: 0, count: 0, months: [12 个全零项] }` |
| 金额含浮点误差 | 合计精确，如 `0.1 + 0.2` 得 `0.3` 而非 `0.30000000000000004` |
| 跨年记录 | 各年互不污染 |

## 7. 界面结构

单页，四个区块，移动端堆叠为单列：

```
┌─────────────────────────────────────────────────────┐
│ 加油记账                              [导出] [导入] │  顶栏
├─────────────────────────────────────────────────────┤
│ 日期 [2026-10-15]  金额 [     ] 元  备注 [        ] │  录入区
│                                            [记下]   │
├─────────────────────────────────────────────────────┤
│ ┌── 本月 ────────┐  ┌── 本年 ─────────┐            │
│ │ ¥1,240.50      │  │ ¥8,930.00       │            │  概览卡
│ │ 4 次 · 均 ¥310 │  │ 28 次 · 均 ¥319 │            │
│ └────────────────┘  └─────────────────┘            │
├─────────────────────────────────────────────────────┤
│ 2026 年 [▾]                                         │
│  ▁▃▅▂▇▁▃▅▂▇▁▃     ← 12 根柱子，点击选中月份         │  统计区
├─────────────────────────────────────────────────────┤
│ 10 月明细                                           │
│  10-15   ¥320.50   中石化                 [删除]    │  明细列表
│  10-08   ¥290.00                          [删除]    │
└─────────────────────────────────────────────────────┘
```

行为约定：

- 页面加载时：年份选择器默认当前年，明细列表默认当前月。
- 点击柱状图的某根柱子 → 下方明细列表切换到该月，被选中的柱子有视觉标记。
- 年份选择器切换 → 概览卡"本年"跟随更新，柱状图重绘，明细列表**保持相同月份**（看 2026-10 时切到 2025 就是 2025-10）。年份选择器存在的意义就是同比，切完跳回 1 月等于把这个用途毁掉。
- 备注：录入区的备注框可选。明细列表中备注非空时以次要样式显示在金额右侧，为空时该行不留空白。
- 记下一笔后：概览卡、柱状图、明细列表立即更新，录入框的金额清空、日期保留（同一天可能连记两笔，但更常见的是隔天记，所以日期**重置为今天**而非保留上次值——避免用户忘了改日期而记错月份）。
- 空状态：无任何记录时，概览卡显示 `¥0.00`，柱状图 12 根零高柱子，明细区显示"还没有记录，在上面记第一笔"。
- 柱状图颜色、字体、间距遵循 `dataviz` 与 `frontend-design` 技能的指引，避免落进 AI 默认配色。零高度的柱子仍保留可见的基线，以表达"这个月没有记录"而非"渲染失败"。

## 8. 错误处理与边界

**最重要的一条：导入必须是"先全量校验、全部通过才替换"。** 绝不能边解析边写入——半路失败会把用户数据毁掉一半，而 localStorage 没有事务、没有备份。因此校验逻辑独立成纯函数：

```js
parseImport(jsonString) -> { ok: true, records: [...] }
                        | { ok: false, error: "人话错误信息" }
```

UI 层只有在 `ok === true` 时才执行覆盖写入。

**拒绝条件**（任一命中即整体拒绝，**现有数据分毫不动**，只弹错误提示，说明是第几条记录哪里不对）：JSON 解析失败、顶层不是对象、`records` 不是数组、`version` 不认识、某条记录的 `date` 不匹配 `YYYY-MM-DD`、某条记录的 `amount` 不是有限正数。

**修复条件**（不拒绝，静默修补）：`id` 缺失或与已有 `id` 重复 → 补发一个新 `id`。理由：`id` 是内部实现细节，用户看不见也不该关心，它坏掉不该导致整份备份被拒收——那会让用户手里唯一的一份备份变成废纸。其余字段没有安全的默认值可用，所以一律拒绝而非猜测。

其余边界：

| 场景 | 处理 |
|---|---|
| localStorage 不可用（Safari 无痕模式） | 顶部常驻黄色横幅警告；降级为内存模式，本次会话可用但刷新即丢；横幅内提示"点导出保存数据"。 |
| 金额为空 / 非数字 / 小于等于 0 | 输入框下方行内红字报错，不提交。输入接受 `/^\d+(\.\d{1,2})?$/`。 |
| 日期为空或格式非法 | 记录不下，行内报错。（日期框默认已填今天，正常不会触发。） |
| 删除记录 | 行内二次确认：点"删除"后该行就地变为"确认删除？[是] [否]"。不用原生 `confirm()`——样式割裂且易误触。 |
| 导出的文件名 | `gasnote-backup-YYYY-MM-DD.json`，内容与 localStorage 存储格式完全一致，保证导出文件可直接用于导入。 |
| 导入成功 | 覆盖前明确告知将替换全部现有记录，覆盖后显示"已导入 N 条记录"。 |

## 9. 测试策略

**采用 TDD：先写失败测试，再写实现。**

单元测试（`node --test`，零依赖）：

- `test/stats.test.js` —— 覆盖第 6 节边界表中的每一行，外加：跨年不污染、2 月（含闰年）、单条记录、`avg` 计算正确性。
- `test/store.test.js` —— 覆盖 `parseImport` 的合法输入；每一种拒绝条件（非 JSON、顶层非对象、`records` 非数组、`version` 不认识、`amount` 为负/零/`NaN`/字符串、`date` 格式错）；以及两种修复条件（`id` 缺失 → 补发、`id` 重复 → 补发且互不相同）。重点断言：拒绝时返回 `ok: false` 且**不产生部分结果**；修补后返回的 `records` 里所有 `id` 唯一。
- 不写单测的部分：`store.load()` / `store.save()` 直接操作 localStorage，不是纯函数，靠第 9 节末尾的手动验收清单覆盖（尤其是"localStorage 里躺着未知版本数据"这条路径）。

不做的事：

- **UI 层不写自动化测试。** 零依赖的前提下搭 DOM 测试环境（jsdom 等）需要引入构建链，成本远超收益，与第 3 节的选型理由直接冲突。
- 作为替代，实现完成后**必须真的启动服务、在浏览器里手动走一遍验收清单**，包括：记一笔、连记多笔、切月份、切年份、删除、导出后重新导入、故意导入一个损坏文件确认数据没被破坏。**在真正跑过之前不宣称完成。**
